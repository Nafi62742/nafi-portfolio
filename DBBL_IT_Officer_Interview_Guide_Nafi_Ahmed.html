Q4. Explain ACID properties in the context of an inter-account fund transfer. What happens if the server crashes mid-way?
Property Banking Meaning Example in ৳10,000 Transfer (A $\rightarrow$ B)
Atomicity All or nothing execution. Debit from A and Credit to B must both succeed. If server fails after debiting A, entire transaction rolls back (`ROLLBACK`).
Consistency Preserves database invariants & balance rules. Account A cannot go below minimum balance or zero; total sum ($A + B$) remains unchanged before & after.
Isolation Concurrent transactions do not interfere. If Account A tries to withdraw while a transfer is happening, row locking prevents double-spending.
Durability Once committed, changes survive system failure. Transaction log (WAL / Redo Log) is written to non-volatile disk before returning success response.

Q6. What is ISO 8583? Why is it vital to DBBL's ATM and POS Switch network?
ISO 8583 is the international standard messaging protocol for Card-Originated Financial Transactions. When a customer inserts a DBBL Nexus or VISA card into an ATM, the ATM converts the PIN, track data, and withdrawal amount into an ISO 8583 formatted message:
  • MTI (Message Type Identifier): e.g., `0100` (Authorization Request), `0110` (Authorization Response), `0200` (Financial Transaction Request).
  • Bitmap: Identifies which Data Elements (DEs) are present in the packet.
  • Data Elements: DE-2 (Primary Account Number), DE-3 (Processing Code), DE-4 (Transaction Amount), DE-11 (System Trace Audit Number - STAN), DE-52 (PIN Data).
3 Core CS, Databases & High Availability
Q7. Why do core banking systems strictly use Relational Databases (Oracle / PostgreSQL / SQL Server) instead of NoSQL (MongoDB / DynamoDB)?
  • Strict ACID Guarantees: Core ledgers cannot tolerate "eventual consistency" where balance updates might lag across nodes. Relational databases provide strong serialization.
  • Relational Integrity: Foreign key constraints prevent orphaned transaction records, invalid account references, or unlinked ledger entries.
  • Complex Multi-Table Joins & Regulatory Audits: Financial audits require multi-table reconciliation queries which are natural in SQL with indexed joins.
  • Where NoSQL IS used in Banking: Storing session states (Redis), audit log ingestion, clickstream analytics, or product catalog lookup (DynamoDB/MongoDB).
Q8. What is Optimistic vs. Pessimistic Locking? When would you use SELECT ... FOR UPDATE?
  • Pessimistic Locking (SELECT ... FOR UPDATE): Locks the selected account row immediately until the transaction commits or rolls back. Other concurrent transactions must wait.
    Bank Use Case: ATM cash withdrawal or balance debit where race conditions cannot be tolerated.
  • Optimistic Locking: Does not lock the row during reading. Instead, it checks a `version` column before updating:
    UPDATE accounts SET balance = 500, version = version + 1 WHERE id = 101 AND version = 3;
    If `rows_affected == 0`, a conflict occurred and the application retries. Best for read-heavy systems with low collision frequency.
Q9. How does Database Indexing work internally, and why shouldn't you index every column?
  • B+ Tree Indexing: Balanced tree data structure allowing $O(\log N)$ search, insertion, and range queries. Leaf nodes are linked as a doubly-linked list for sequential scans.
  • Write Penalty on High-Frequency Tables: In high-throughput banking transaction tables, every `INSERT` or `UPDATE` forces the database engine to update all associated index trees and rebalance nodes, degrading write performance significantly.
4 System Design & Security Scenarios
Q10. System Design Scenario: How would you architect DBBL's ATM backend to handle 10x traffic surges during Eid without crashing or double-debiting?
Architectural Blueprint:
  1. Read/Write Separation: Direct account balance inquiries and mini-statement reads to Read Replicas or a fast Redis cache cluster. Reserve the Primary Master Database strictly for financial write transactions.
  2. Connection Pooling: Use database connection poolers (like PgBouncer / HikariCP) to prevent thousands of ATM terminals from overwhelming database thread limits.
  3. Asynchronous Non-Critical Pipelines: Offload SMS alerts, email receipts, push notifications, and analytics to a message broker (Kafka / AWS SQS / RabbitMQ).
  4. Circuit Breaker Pattern: If downstream core banking services experience latency, circuit breakers (e.g. Resilience4j) fail fast with graceful user messaging instead of hanging ATM hardware.
Q11. What is the difference between Symmetric vs. Asymmetric Encryption, and how are they used in banking?
  • Symmetric Encryption (AES-256): Same secret key for both encryption and decryption. Very fast. Used for encrypting database data-at-rest and ATM PIN blocks (in HSM - Hardware Security Modules).
  • Asymmetric Encryption (RSA / ECC): Public key encrypts, private key decrypts. Slower. Used for TLS/SSL handshake, digital signatures, and securely exchanging the symmetric session key.
  • Hashing (bcrypt / Argon2 / SHA-256): One-way cryptographic transformation with salt. Used for storing passwords and PIN verification.

Q1. You integrated SSLCommerz in RunMate Club. Walk us through a secure payment gateway handshake from user checkout to database commit.
Handshake Steps:
  1. Initiation: Client initiates checkout $\rightarrow$ Backend generates unique `tran_id` and calls SSLCommerz `gwprocess` API with credentials and server-to-server callback URLs.
  2. Redirect & Authorization: User completes 2FA on hosted gateway (Nexus/Rocket/Cards).
  3. IPN (Instant Payment Notification): SSLCommerz sends server-to-server POST to backend IPN webhook with `val_id` and transaction parameters.
  4. Server-Side Validation: Backend queries SSLCommerz validation endpoint using `val_id` to verify currency, status (`VALID`), and exact amount match.
  5. Idempotent Ledger Update: In an atomic SQL transaction (`BEGIN ... COMMIT`), invoice status is updated from `PENDING` to `PAID`. Duplicate IPN triggers with identical `tran_id` are ignored.
Key Bank Concept: Idempotency Key & Zero Trust Client-Side Redirects (Never fulfill balances based solely on browser return URL).

  • Maker-Checker Principle: Banking regulation (Bangladesh Bank ICT Guideline) states that no single officer can create and finalize a financial transaction. A Maker initiates the record (Status: `PENDING_APPROVAL`), and a Checker (Branch Manager / Approver) verifies and authorizes it.

Q5. What is the Mutating Table Error (ORA-04091) in PL/SQL triggers, why does it occur, and how do you resolve it?
  • Cause: Occurs when a row-level trigger (BEFORE/AFTER INSERT/UPDATE FOR EACH ROW) attempts to query or modify the exact same table that fired the trigger. Oracle raises ORA-04091: table is mutating, trigger/function may not see it to prevent inconsistent views of data.
  • Resolution Methods:
    1. Compound Trigger (Oracle 11g+): Combines `BEFORE STATEMENT`, `BEFORE EACH ROW`, `AFTER EACH ROW`, and `AFTER STATEMENT` in a single trigger block where variables hold data until statement completion.
    2. Autonomous Transaction Trigger: Declaring `PRAGMA AUTONOMOUS_TRANSACTION` inside the trigger allows an independent read session.
    3. Statement-Level Trigger: Moving the validation logic to `AFTER STATEMENT` trigger where the table is no longer mutating.
Q6. What is PRAGMA AUTONOMOUS_TRANSACTION? Why is it vital for banking audit logs and security exception logging?
  • Definition: An autonomous transaction is an independent transaction started by an existing parent transaction. It can perform DML, commit or rollback without affecting the parent transaction state.
  • Banking Use Case: When an unauthorized transfer or invalid PIN entry causes a fund transfer procedure to fail and rollback (`ROLLBACK`), the failed attempt record in `AUDIT_SECURITY_LOGS` must still be COMMITTED permanently for fraud detection.
CREATE OR REPLACE PROCEDURE log_audit_trail (
  p_account_no IN VARCHAR2, p_action IN VARCHAR2, p_status IN VARCHAR2
) AS
  PRAGMA AUTONOMOUS_TRANSACTION; -- Independent commit scope
BEGIN
  INSERT INTO audit_logs(account_no, action, status, log_time)
  VALUES (p_account_no, p_action, p_status, SYSDATE);
  COMMIT; -- Commits ONLY the audit entry, parent transaction remains uncommitted
END log_audit_trail;
Q7. How do BULK COLLECT and FORALL eliminate context switching in high-volume banking batch jobs?
  • Context Switching Problem: In standard row-by-row cursor loops, every row forces a CPU context switch between the PL/SQL runtime engine and the SQL database engine. Processing 1,000,000 accounts takes millions of context switches.
  • Bulk Processing Solution: BULK COLLECT fetches rows in memory arrays (batches of 1,000 or 5,000 using the `LIMIT` clause), and FORALL dispatches bulk DML statements back to the SQL engine in a single batch call.
DECLARE
  TYPE t_acc_list IS TABLE OF accounts.account_id%TYPE;
  v_acc_ids t_acc_list;
  CURSOR c_dormant IS SELECT account_id FROM accounts WHERE last_tx_date < ADD_MONTHS(SYSDATE, -24);
BEGIN
  OPEN c_dormant;
  LOOP
    FETCH c_dormant BULK COLLECT INTO v_acc_ids LIMIT 1000; -- Batch fetch
    EXIT WHEN v_acc_ids.COUNT = 0;
    
    FORALL i IN 1..v_acc_ids.COUNT -- Single bulk update to SQL engine
      UPDATE accounts SET status = 'DORMANT' WHERE account_id = v_acc_ids(i);
    COMMIT;
  END LOOP;
  CLOSE c_dormant;
END;

WITH RankedTransactions AS (
  SELECT branch_id, account_no, amount, tx_date,
         DENSE_RANK() OVER (PARTITION BY branch_id ORDER BY amount DESC) as rank_pos
  FROM transactions
  WHERE tx_status = 'SUCCESS'
)
SELECT branch_id, account_no, amount, tx_date
FROM RankedTransactions
WHERE rank_pos = 2;
Q9. Write a SQL query to calculate a Customer's Continuous Running (Cumulative) Balance for an account statement. 
SELECT 
  tx_id, tx_date, tx_type, amount,
  -- Cumulative running sum partitioned by account
  SUM(CASE WHEN tx_type = 'CREDIT' THEN amount ELSE -amount END) 
    OVER (
      PARTITION BY account_no 
      ORDER BY tx_date, tx_id 
      ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS running_balance
FROM transactions
WHERE account_no = '017110002341'
ORDER BY tx_date ASC, tx_id ASC;

Q14. What is the difference between Nostro, Vostro, and Loro Accounts in International Banking?
  • Nostro Account (Latin: "Our money with you"): An account that a domestic bank (DBBL) maintains in foreign currency in another foreign bank overseas.
    Example: DBBL maintains a USD account at JPMorgan Chase Bank, New York to settle international foreign remittances and import Letters of Credit (L/C).
  • Vostro Account (Latin: "Your money with us"): An account that a foreign bank maintains in local currency (BDT) at a domestic bank (DBBL).
    Example: Citibank NA London maintains a BDT account at DBBL Dhaka to disburse foreign remittances to beneficiaries across Bangladesh.
  • Loro Account (Latin: "Their money"): A third-party bank's account referenced during bilateral interbank settlements (e.g., Bank A settling through Bank B's Nostro account at Bank C).

5 Database Architecture, CBS & Switch Protocols (20-27 mins)
Q17. Explain Oracle Database Architecture: SGA (System Global Area) vs. PGA (Program Global Area) and Redo Log vs. Undo Segments.
  • SGA (Shared Memory across all database processes):
    • Database Buffer Cache: Caches data blocks read from disk.
    • Shared Pool: Stores parsed SQL execution plans (Library Cache) and table metadata (Dictionary Cache).
    • Redo Log Buffer: Circular buffer recording all database changes before flushing to disk.
  • PGA (Private Memory allocated per server process): Stores session variables, user sorting areas (ORDER BY), and hash join tables.
  • Redo Log vs. Undo Tablespace:
    • Redo Logs (Roll-Forward / Crash Recovery): Record all committed transactions to replay changes in case of power failure or crash.
    • Undo Segments (Rollback & MVCC): Store before-images of modified data. Enables transaction `ROLLBACK` and provides Multi-Version Concurrency Control (MVCC) so readers never block writers.
Q18. What is Optimistic vs. Pessimistic Locking? When would you use SELECT ... FOR UPDATE in banking?
  • Pessimistic Locking (SELECT ... FOR UPDATE): Explicitly acquires an exclusive row lock on the customer's account row. Any other concurrent transaction attempting to read/update the row must wait until transaction commit/rollback.
    Bank Use Case: ATM cash withdrawals, balance debits, POS swipe authorization where race conditions can cause double-spending.
  • Optimistic Locking: Does not hold database locks. Checks a version column: UPDATE accounts SET balance = 500, version = version + 1 WHERE id = 101 AND version = 3;. If rows affected = 0, conflict is detected and the request retries. Best for read-heavy portals with rare simultaneous writes.

Q20. Explain the ISO 8583 message structure and its role in DBBL's ATM and POS Switch network.
ISO 8583 is the universal banking messaging standard for card transactions across ATMs, POS terminals, and Switch gateways:
  • MTI (Message Type Identifier): 4-digit header:
    • 0100: Authorization Request (e.g. POS card swipe balance check) | 0110: Authorization Response.
    • 0200: Financial Transaction Request (e.g. ATM cash withdrawal) | 0210: Financial Transaction Response.
    • 0420: Transaction Reversal Advice (e.g. ATM hardware jam after debit).
  • Bitmap: Binary field array indicating which Data Elements (DEs) are packaged in the payload.
  • Key Data Elements: DE-2 (Card PAN), DE-3 (Processing Code), DE-4 (Amount), DE-11 (System Trace Audit Number - STAN), DE-52 (Encrypted PIN Block).
Q21. Scenario: A customer withdraws ৳10,000 from a DBBL ATM using another bank's card. Their account is debited, but the ATM encounters a hardware jam and dispenses no cash. Walk us through the technical resolution.
  1. Immediate Automated Reversal: The ATM cash dispenser sensor detects non-dispense and automatically dispatches an ISO 8583 0420 (Reversal Advice) to the DBBL Switch $\rightarrow$ NPSB $\rightarrow$ Issuing Bank to release the hold immediately.
  2. Electronic Journal (EJ) & Cash Audit: If network drops prevent 0420 delivery, the event is permanently logged in the ATM's internal Electronic Journal (EJ) file with error code (e.g. BILL_DISPENSER_ERROR).
  3. Daily Reconciliation: During nightly ATM cash balancing, the physical excess cash in the ATM cassette matches the unreconciled debit in the Switch log.
  4. Chargeback & Settlement: The issuing bank raises a chargeback claim via NPSB portal; DBBL IT reconciles the EJ log and authorizes settlement credit back to customer within regulatory TAT (72 hours).
6 High Availability, Infrastructure & PCI-DSS (27-33 mins)
Q22. What is RPO vs. RTO, and how does Synchronous vs. Asynchronous Database Replication affect Disaster Recovery (DR)?
Metric Full Form Banking Meaning Target in DBBL Mission-Critical CBS
RPO Recovery Point Objective Maximum acceptable data loss measured in time. RPO = 0 (Zero financial transaction data loss allowed).
RTO Recovery Time Objective Maximum acceptable downtime before service restoration. RTO < 15-30 minutes for automated DR failover.
  • Synchronous Replication (Oracle Data Guard / Max Availability): Master commits only after Standby acknowledges log write. Ensures Zero Data Loss (RPO=0), but adds network latency.
  • Asynchronous Replication: Master commits immediately; sends logs in background. Lower latency, but risks minor transaction data loss if primary DC suffers catastrophic power outage.

7 Crisis Scenarios, Machine Learning & Behavioral (33-40 mins)
Q24. Crisis Scenario: At 11:30 PM, multiple branches and FastTrack ATM booths report that customer transactions are timing out with "Unable to process" errors. Walk us through your step-by-step diagnostic procedure.
Structured 5-Step Incident Triage:
  1. Isolate Scope: Check monitoring dashboards (Grafana / Prometheus / Zabbix) — Is the issue isolated to a specific ISP, a single region, ATM switch, or the Core Banking database?
  2. Check Network & Switch Layer: Test connectivity to Switch and Core Banking middleware (ping, traceroute, check BGP router links and switch message queues for backpressure).
  3. Inspect Database Health: Log into database server and check active blocking locks, deadlocks, connection pool exhaustion (pg_stat_activity / v$session_wait), and disk tablespace capacity.
  4. Mitigate & Failover: If primary DB thread lockup is identified, execute clean failover to Standby node or restart stalled middleware connection poolers.
  5. Post-Mortem & Log Audit: Analyze syslog, application logs, and database trace files to determine root cause (e.g. unindexed query executed by night batch job) and implement permanent preventive patches.
